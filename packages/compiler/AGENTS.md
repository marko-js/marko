# `@marko/compiler`

Translator-agnostic compiler: parses `.marko` into a Babel AST (custom node types like `MarkoTag`, `MarkoAttribute` — added to Babel by the root `patches/`), runs migrate/transform passes, then hands the AST to a **translator** (`@marko/runtime-tags/translator` or `marko/translator`) for codegen. Stays at v5.x; language changes belong in the translators, not here.

## Map

- `src/index.js` — public API: `compile[File][Sync](src, filename, config)` → `{ code, map, meta, ast }`, `configure`, `taglib`, `types`.
- `src/config.js` — option defaults (`config.d.ts` declares every option), and the `globalConfig` that `configure()` sets (both re-exported by `index.js`). A default read outside a compile's own config (e.g. `getRuntimeEntryFiles`, `taglib.buildLookup`) comes from `globalConfig`, never the default export.
- `src/babel-plugin/` — pipeline core. Stages: `parse → migrate → transform → analyze` (cached per template) then `translate` on a clone. Taglib visitors run in `migrate`, `transform` and `translate` — including those from the taglibs a translator registers via `taglibs`/`optionalTaglibs`, which is how a translator contributes migrators. The compiler runs the translator's `transform` and `analyze` (both optional) and `translate`; there is no `translator.migrate`. A tag definition's `analyze` hook runs only where the translator dispatches it (runtime-tags' `visitors/tag`); an `analyze` key at a `marko.json` root is ignored. Taglib `translate` is skipped for `output: "hydrate"`.
- `src/taglib/` — tag registry and discovery, in TypeScript (checked by the package `tsconfig.json`, and by `types.test.d.ts` against the published `babel-utils.d.ts` types). Resolution order is documented on `Registry` and `Layer` in `lookup.ts`. Invariants: finding a directory's lookup costs one `package.json` stat; a nearer definition never replaces one of the translator's own tags but merges into it, keeping its hooks (the interop relies on this for class components named like Marko 6 core tags); tag definitions keep only what something reads; each file system gets its own registries, and a compile passes its `fileSystem`; caches are dropped only whole (`clearCaches`, `register`, `excludeDir`, `excludePackage`), which only adding or removing files or editing JSON calls for, never editing a template.
- `src/babel-utils/` — the helper API for translator authors (`assert*`, `diagnostic*`, `import*`, `parse*`, `getTagDef`, `isNativeTag`, `resolveTagImport`, ...). Exported as `@marko/compiler/babel-utils`.
- `internal/babel/index.ts` — the single controlled Babel entry, re-exported as `@marko/compiler/internal/babel`. All Babel access (here and in translators) goes through it, never `@babel/*` directly.

## Translator contract

A translator module exports `translate` (required visitor), `taglibs` (required, `[[id, props]]`), `tagDiscoveryDirs` (required), optional `transform`/`analyze` visitors, `optionalTaglibs`, `classTaglibs` (applies the class API taglib rules in `taglib.ts` › `loadClassTagDir`; defaults to `tagDiscoveryDirs.includes("components")`), `preferAPI` (`"tags"` | `"class"`), `version`, `getRuntimeEntryFiles(output, optimize)`, and `cheatsheet` (module-relative path to an LLM syntax reference). `config.translator` selects it, else `config.js` detects it from the app's dependencies (`util/try-load-translator.js`).

## Notes

- `output: "source"` / `"migrate"` re-print `.marko` source (tooling/codemods) — no translator codegen.
- Bumping any `@babel/*` version requires regenerating the corresponding patch in root `patches/` (pnpm patchedDependencies); the custom AST types and generated `dist/types.d.ts` (`pnpm --filter @marko/compiler run build-babel-types`) depend on them.
- `util/agent-fix-guide.js` appends a pointer to the translator's `cheatsheet` to compile errors when it detects a coding-agent environment (`CLAUDECODE`, `AI_AGENT=1`, …); `MARKO_AGENT_FIX_GUIDE=0` suppresses it and any other value forces it. It fires only for a translator given as a module id, so fixtures compiled with an inline translator object snapshot the same under an agent; a test of the guide forces it (`packages/runtime-tags/src/__tests__/main.test.ts` › `forceCodingAgent`).
- A compile `cache` keeps each template as analyzed (parse through `analyze`), keyed by translator and template id and revalidated against its content and the watched files of it and every template its analysis read (`hasStaleDependency`). Configs may share one only when they differ in `output` alone, as the bundler plugins' do: nothing before `translate` may read `output` or import an output-specific runtime path. Omitting `cache` uses one process-wide Map (`src/config.js`), so a test compiling under several configs gives each its own `cache: new Map()`.
