# Performance

Runtime speed and bundle size opportunities. Format and rules: [README.md](README.md).

## Derive await/try branch scope owners without serialization

`packages/runtime-tags/src/translator/util/signals.ts:1330` | 2026-07-02 | impact:low | effort:high

State-driven `<if>`/`<for>` branches now link their owner from resume markers instead of serializing it, but `<await>`/`<try>` branches still serialize `_: _scope_with_id(parentScopeId)`. Two blockers were verified: (1) their branch machinery can be tree-shaken out of resume bundles while closures into the content still fire (`await-tag` fixture: `_await_promise` is dropped, `branchesEnabled` stays off, so branch visits are never processed), and (2) reordered/out-of-order content pushes scope data and closure subscriptions a flush earlier than its markers, so a state update mid-stream can read the owner before it could be linked. Solving these likely means an explicit enable in the resume payload and deferring subscriptions to marker processing.

`packages/runtime-tags/src/html/writer.ts:588` | 2026-07-02 | impact:low | effort:med

Existing TODO in `_if`, but narrower than it reads: branch index 0 is already elided (`branchIndex || undefined`), and the `return <index>` statements are only appended to branches whose `kBranchSerializeReason` is truthy, so a conditional whose branches never serialize writes nothing. The remaining waste is an `else`/`else-if` branch (index > 0) serialized for a reason unrelated to branch swapping (e.g. hoist-through) under a condition that can never change and with no direct closures (`_if_closure` reads the index at `src/dom/signals.ts:245`, the `_if` signal at `src/dom/control-flow.ts:433`). ## Avoid resume-registering native tag change handlers

`packages/runtime-tags/src/translator/visitors/function.ts:108` | 2026-07-02 | impact:med | effort:high

Existing TODO: plain `on*` event handlers on native tags skip registration, but controllable change handlers (`valueChange=`, `checkedChange=`, ...) always go through `_resume` registration, costing a registry id + registration statement in server output and a registry entry client-side for every controllable input. The registration is currently load-bearing, not incidental: the handler function itself is serialized as a `ControlledHandler` scope prop (`packages/runtime-tags/src/html/attrs.ts:430`) that the shared typed resume effects (`_attr_input_checked_script` and friends in `src/dom/controllable.ts`) read when the user interacts before any re-render, and serializing a function requires it to be registered. Removing the registration means restructuring controllable resume so a per-section registered effect rebuilds the handler closure from serialized state (the way `on*` handlers work) instead of one shared runtime effect per controllable type reading a serialized function. Touches the ~30 controllable fixtures; needs deliberate design, not a spot fix.

## Specialize dynamic tags statically known to be renderers

`packages/runtime-tags/src/translator/util/tag-name-type.ts:187` | 2026-07-03 | impact:low | effort:high

`<${input.component}/>` style dynamic tags always compile against the fully general `_dynamic_tag` runtime, which includes string-tag (native element) handling, attr normalization for both shapes, and `attrTags` merging. `analyzeTagNameType(tag, true)` already distinguishes the domain: `link ? "a" : "span"` resolves to `NativeTag` (always a string), `flag ? A : B` (imported templates) to `CustomTag` (always a renderer), `input.tag` to `DynamicTag` (either).

Splitting `_dynamic_tag` into a `_dynamic_renderer` (renderer-only, skips the native/`_attrs`/form-control path) selected for `CustomTag` names was implemented and measured, and it is a **net size regression** — do not re-attempt it in this form. Every dynamic-tag fixture grew (+9 to +144 brotli, dom); the example-app aggregate `*` grew +25; none shrank. Two reasons: (1) the "heavy" code the split targets (`_attrs`, native-element serialization, the textarea/select/input form-control runtime) is **shared with ordinary native tags**, so any template containing any HTML keeps it bundled regardless of how its dynamic tags compile; the code actually unique to the string branch of `_dynamic_tag` is small. (2) A delegation structure (generic `_dynamic_tag` reuses a shared renderer impl so renderer logic is not duplicated, `patchDynamicTag` patches both entry points so class interop stays correct) is required for correctness and to avoid duplication, but the extra factory/signal boundaries and the second patched export cost more than the string branch saves. A payoff would require a bundle that has renderer-only dynamic tags **and no native tags at all** — rare enough that the example apps do not exercise it. The behavior-preserving delegation refactor itself is sound (full suite green, zero render.md diffs) if a future need makes the split worthwhile; the problem is purely that there is nothing to tree-shake in realistic bundles.

## Compile non-nullable string dynamic tags as native elements

`packages/runtime-tags/src/translator/visitors/tag/dynamic-tag.ts` | 2026-07-03 | impact:med | effort:high

The always-string direction (`link ? "a" : "span"`) is a **substantial** win, but only when compiled as a real native element rather than by swapping which runtime function the branch calls. The key invariants: a non-nullable string tag name means the element always exists (no control flow), and a rename is a move, not a re-render (create the new element, transfer attributes and children, update the scope reference) since the body's signals hold direct node references. So it compiles like a native tag whose name is a runtime expression, dropping the entire `_dynamic_tag` branch subtree: `createBranchWithTagNameOrRenderer` (dynamic element creation), `normalizeDynamicRenderer`, `_attrs`/`_attrs_content`, the content-renderer path, and `_resume_dynamic_tag`. Measured runtime delta (built `dist/dom.mjs`, same rolldown+minify+brotli as `build:sizes`): **−2268 brotli** when the dynamic native tag is the sole consumer of that machinery, **−2110** when the app also uses `<if>`/`<for>`, **−1106** in the pessimistic floor where `_attrs` and branches are already pulled by other features. Net-positive in every case (unlike the renderer split above), plus the user code shrinks (per-attr signals instead of the `_dynamic_tag` call + attrs object) and SSR stops compiling the body as a client renderer.

A one-line runtime primitive carries the rename: `_dynamic_native_tag(scope, accessor, name)` — if `el.tagName.toLowerCase() !== name`, create `document.createElementNS(ns, name)`, move attribute nodes (`while (el.attributes.length) next.setAttributeNode(el.attributes[0])`) and children (`next.append(...el.childNodes)`), `el.replaceWith(next)`, and update `scope[accessor]`. Namespace handling mirrors `createBranchWithTagNameOrRenderer` (svg/math/inherit).

Implementation path (validated by exploration, not yet landed): keep the tag classified `DynamicTag` and add a gated branch to `dynamic-tag.ts` analyze+translate rather than touching `native-tag.ts` (which is built entirely around a compile-time-constant tag name via `getCanonicalTagName`/`getTagName` and switches on it for void/select/textarea/head/body — a rewrite to thread a runtime name through). Keep `node.name` as the expression so reference tracking populates its `referencedBindings`. Analyze: create an element binding (`createBinding("#" + defaultName, dom, section)`) instead of the `#text` marker, and skip the dynamic-tag `addSetupStatement`. DOM translate: `walks.visit(tag, WalkCode.Get)`, `write\`<${defaultName}></${defaultName}>\``, per-attr signals mirroring native-tag (`\_attr_class`/`\_attr_style`/`\_attr`via`addStatement("render", …, value.extra.referencedBindings, …)`), then the swap signal `addStatement("render", …, node.name.extra.referencedBindings, \_dynamic_native_tag(scope, accessor, node.name))`. HTML translate: interpolate the real name into the open/close tag (`write\`<${node.name}…>…</${node.name}>\``); hydration reads the name from `element.tagName`so nothing extra is serialized. DOM and HTML must land together (existing enumerable-native fixtures like`dynamic-tag-multiple`'s `isLarge ? "h1" : "h2"`change output, so a DOM-only slice breaks SSR/hydration). Gate: non-nullable,`NativeTag`type, statically enumerable string literals, all safe (exclude form controls — value/checked live as properties a rename would drop — void elements, and svg/math/html/head/body/script/style/textarea/template/etc.), no body (stage 1), no var/args/spread/event/change-handler attrs; anything outside the gate falls back to today's`\_dynamic_tag`. Stage 2 extends to the with-body case (inline body in the clone template + move children on rename, the mechanism `<show>` already uses to relocate a body without re-rendering).

Related: these body-oriented optimizations may extend to **custom tags** proven to render their `content` unconditionally exactly once — the parent could place the body inline (reusing the `<show>`-style move / the existing `kDirectContent`/`_dynamic_tag_content` direct-content machinery in `dynamic-tag.ts`) instead of passing a separate content renderer. Needs cross-template analysis of the child's body-usage pattern (a sibling of the empty-setup elision analysis). Evaluate once the dynamic-native path exists and its runtime primitive is known.

## Parallel test workers oversubscribe cores via rolldown's thread pool

`scripts/test-parallel.js:40` | 2026-07-02 | impact:low | effort:med

`npm run test:parallel` runs one mocha process per core, but each fixture bundle already drives rolldown's own multi-threaded build (`packages/runtime-tags/src/__tests__/utils/bundle.ts`), so even a serial run uses ~1.4 cores. On a 4-core box the whole suite lands at ~87s vs ~238s serial (2.7×), short of the ~4× the core count implies, because the workers contend for the same native threads. `RAYON_NUM_THREADS=1` in the worker env made no measurable difference, so rolldown isn't honoring it. If rolldown (or its native binding) exposes a per-build thread cap, pinning workers to 1 bundler thread each — so N workers ≈ N threads total — could recover much of the lost efficiency and let the runner scale closer to linearly on higher core counts.
