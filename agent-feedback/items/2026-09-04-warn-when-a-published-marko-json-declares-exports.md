# Warn when a published `marko.json` declares `exports` without `script-lang`

A tag library published with a `marko.json` that omits `"script-lang": "ts"` loses its entire type surface for every consumer: the language tools hard-code JavaScript for any path under `node_modules`, so the library's `export interface Input` is never read and a wrong-prop call type-checks clean, with no diagnostic at all whenever the consumer has `noImplicitAny` off. Nothing in this repo signals it — `TaglibLoader.scriptLang` stores `taglib.scriptLang` and no code here reads that field back, the compiler always enables Babel's `typescript` parser plugin so the library's TS-only syntax compiles without comment, and `packages/runtime-class/docs/custom-tags.md § Publishing tags to npm` and `marko-json.md § Tag library definition › Options` both show and enumerate the publishing `marko.json` without `script-lang` at all. The intent comment at this site is itself wrong about the fallback: it says the tools "check for a tsconfig", but a tsconfig shipped inside the package is ignored outright for anything under `node_modules`, so it steers a maintainer away from the real failure. The loader already owns the marker that identifies a published tag library — its `exports` handler is gated on `taglib.isFromPackageJson` or a `node_modules` path — so after `propertyHandlers` runs in `TaglibLoader.load`, a taglib that declared `exports` but left `scriptLang` undefined should warn that consumers will see its tags' input as `any` unless `script-lang` is set. Correct the comment in the same change and add the requirement to both docs. The `node_modules` rule itself lives in marko-js/language-server; the missing signal, the config key's definition and the docs that model the incomplete `marko.json` are all here.

Check: In an empty dir run `npm i marko@6 @marko/type-check typescript`, add `"my-lib": "1.0.0"` to dependencies, and create `node_modules/my-lib/package.json` = `{"name":"my-lib","version":"1.0.0"}`, `node_modules/my-lib/marko.json` = `{"exports":"./tags"}`, and `node_modules/my-lib/tags/my-tag.marko` starting with `export interface Input { foo: string }`. With `index.marko` = `<my-tag foo=123/>` and a tsconfig setting `strict` plus `noImplicitAny: false`, `./node_modules/.bin/mtc` exits 0; adding `"script-lang": "ts"` to that `marko.json` makes the same run report `TS2322: Type 'number' is not assignable to type 'string'`. With `noImplicitAny` on, the only diagnostic is `TS7016`, which blames the consumer and never names `script-lang`.
