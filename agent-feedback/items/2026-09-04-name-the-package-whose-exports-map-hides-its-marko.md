# Name the package whose `exports` map hides its `marko.json`, instead of suggesting a native tag

`findWithMeta` discovers a dependency's taglib with `markoModules.tryResolve` on `<name>/marko.json`, and `tryResolve` is `resolve-from`'s silent variant, so it swallows every resolution error. A published component library whose `package.json` `exports` map omits `"./marko.json"` therefore has its entire taglib dropped without a word, and the consumer — who cannot fix the library — is told ``Unable to find entry point for custom tag `<my-button>`. Did you mean `<button>`?``, a suggestion that points at a native HTML element and reads as a typo in their own template. The trap is sharpened by `"./marko.json"` being the only entry the exports map gates, since the tag templates it names are read straight off disk: an author who exports `"."` and `"./tags/*"` and nothing else — the natural assumption that exports govern JS imports, not compiler config — still loses every tag. The information needed to say the right thing is already available and thrown away: `markoModules.resolve` is exported and non-silent, and its `ERR_PACKAGE_PATH_NOT_EXPORTED`, whose message names the offending `package.json`, is cleanly distinguishable from the `MODULE_NOT_FOUND` a dependency with no taglib produces, so no filesystem heuristic is needed. Catch that error code in the finder and carry the package name into `packages/runtime-tags/src/translator/visitors/tag/custom-tag.ts › tagNotFoundError` so the message names the package and the missing exports entry in place of the did-you-mean, and add the requirement to `packages/runtime-class/docs/custom-tags.md § Publishing tags to npm`, which states only that the package must include a `marko.json` at its root.

Check: In an app depending on `my-lib`, with `node_modules/my-lib/marko.json` = `{"<my-button>":{"template":"./tags/my-button.marko"}}`, a `tags/my-button.marko` beside it, and `node_modules/my-lib/package.json` = `{"exports":{".":"./index.js","./tags/*":"./tags/*"}}`, `pnpm run compile -- -o html -d /abs/index.marko` on `<my-button>Hi</my-button>` reports ``Did you mean `<button>`?``; adding `"./marko.json": "./marko.json"` to that exports map is the only change that makes it compile, and removing `"./tags/*"` does not break it. In a fresh node process, `Module._resolveFilename("my-lib/marko.json", …)` from the app dir throws `ERR_PACKAGE_PATH_NOT_EXPORTED` while a dependency with no taglib throws `MODULE_NOT_FOUND` (a warm package.json cache masks the difference).
