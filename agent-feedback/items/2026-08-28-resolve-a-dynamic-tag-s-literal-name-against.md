# Resolve a dynamic tag's literal string name against the taglib

Every void-element check, in `analyze.exit`, in both `translate` exits and in the `seen.content` guard in `analyze.enter`, is keyed on `getTagDef(tag)?.parseOptions?.openTagOnly`, which resolves only for a name written literally in the source, so a dynamic tag whose name is a static string literal loses all of them: `<${"br"}/>`, `<${"img"} src="x.png"/>` and `<${"input"} name="a"/>` compile to `<br></br><img src=x.png></img><input name=a></input>` in both outputs with no compile error, no runtime error and no `MARKO_DEBUG` assertion. That markup is not equivalent to the literal form, because the HTML spec turns a `</br>` end tag into a second `<br>`, so parse5 yields four elements where the translator counted three, and the client walk goes with it: `<${"br"}/>` followed by `<div>${input.x}</div>` compiles to `$template = "<!><br></br><div> </div>"` with `$walks = over(2), next(1), get, out(1)`, so `next(1)` lands on the `<div>` element instead of its text child and every later op is one node short. The failure is hard, not cosmetic: a debug build records the accessor as `#div/0`, so `$scope["#text/0"]` is undefined and `packages/runtime-tags/src/dom/dom.ts › _text` throws `TypeError: Cannot read properties of undefined (reading 'data')`, while an optimized build writes `.data` onto the `<div>` and silently renders the interpolation nowhere; any client-rendered branch reaches it, since `<if=show><${"br"}/><div>${input.x}</div></if>` compiles its branch to the same template and walks pair, and an SSR page escapes the desync through its resume markers but still ships the extra `<br>`. Resolve the tag def from `packages/runtime-tags/src/translator/util/get-tag-name.ts › getTagName`, which already returns `"br"`/`"input"` for these names and is what `getCanonicalTagName` uses to write the open tag; that also restores the literal-form compile errors, since `<${"input"}><span>x</span></>` renders `<input><span>x</span></input>` and `<${"input"} content=Slot/>` renders `<input><b>s</b></input>` where the literal spellings are rejected at compile time by that same `seen.content` guard. A regression fixture wants `<${"br"}/>` plus a following bound node so the `$template` and `$walks` snapshot pins the node count; `dynamic-tag-native-variants` uses a `<let>`-bound name and a non-void `<${"select"}>`, so nothing covers the literal void combination.

Check: `pnpm run compile -- -o html -d <file>` on `<${"br"}/><${"img"} src="x.png"/><${"input"} name="a"/>` emits `_html("<br></br><img src=x.png></img><input name=a></input>")` with no diagnostic, and parse5 `parseFragment` of that string reports 4 childNodes `['br', 'br', 'img', 'input']` with 0 parse errors. Walk desync: `-o dom` on `<${"br"}/>` plus `<div>${input.x}</div>` gives `$template = "<!><br></br><div> </div>"` and `$walks = over(2), next(1), get, out(1)` against a 4-node parse, and mounting that template in jsdom throws `TypeError: Cannot read properties of undefined (reading 'data')` from `_text`; the literal `<br/>` gives `"<br><div> </div>"` with `over(1), next(1)` and binds the text node.
