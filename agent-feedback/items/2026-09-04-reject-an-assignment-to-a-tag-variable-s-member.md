# Reject an assignment to a tag variable's member instead of rewriting it as a read

`trackReference` walks up member expressions and calls `addReadToExpression` without ever checking whether the root identifier sits in an assignment or update target, so `settings.theme = "light"` on a `<let>`/`<const>` object compiles as a _read_ of `settings.theme` and produces two silently wrong outputs. When the member is read reactively the assignment becomes a bare `$scope.settings_theme = "light"`: the user's object is never mutated, no signal runs, and the `scope[valueAccessor] !== value` dirty check in `packages/runtime-tags/src/dom/signals.ts › _const` is left holding the new value, so the documented reassignment fix (`settings = { ...settings, theme: "light" }`) is dropped afterwards too and the DOM stays stale for the life of the scope. When the member walk breaks early on a sibling method call (`ctx.fillRect(...)`), the identifier rewrite still applies to the assignment target and the compiler emits `$scope.ctx?.fillStyle = "red"`, which is not valid JavaScript, in both `-d` and optimize. The identifier form of the same mistake already hard-errors through `packages/runtime-tags/src/translator/util/assert.ts › assertNoTagVarMutation`, and `getReadReplacement` already bails on `extra.assignment` for identifiers, so mark member assignment and update targets the same way and reject them, or `diagnosticWarn` naming the reassignment idiom the way `packages/runtime-tags/src/translator/core/script.ts` already warns about the discarded-cleanup habit. A `MARKO_DEBUG` `Object.freeze` is not a substitute: the assignment is rewritten off the object entirely, and a purely derived `<const>` never stores the object in scope at all, so there would be nothing frozen to catch — freeze would reach only `items.push(x)`, the one form the cheatsheet's DON'T table already names.

Check: `pnpm run compile -- -o dom -d /abs/a.marko`, where `a.marko` is `<const/ctx=input.ctx>` plus `<script>{ ctx.fillStyle = "red"; ctx.fillRect(0, 0, 1, 1); }</script>`, emits `$scope.ctx?.fillStyle = "red"` and `node --check` on the output reports `SyntaxError: Invalid left-hand side in assignment`. The same command on `<let/settings={ theme: "dark" }>` plus `<div>${settings.theme}</div>` plus `<button onClick() { settings.theme = "light" }>x</button>` emits `$scope.settings_theme = "light"` with no call into the `settings` signal; the nested (`settings.a.b = …`) and computed (`o["theme"] = …`) spellings compile the same way.
